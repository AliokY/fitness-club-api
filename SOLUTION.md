# Реализованная часть решения

Состояние: 28 октября 2026 года. Реализованы все восемь эндпоинтов ТЗ: создание, карточка, изменение и отмена брони, расписание, аналитика загрузки залов и оба маршрута очереди ожидания.

## Поведение

Маршрут требует JWT, обязательные `classId`, `seats` и непустой `Idempotency-Key`. Ответ `201` содержит только `id`, `classId`, `seats`, `status`, `createdAt`. Идентификатор пользователя берётся из токена. Неизвестные поля JSON игнорируются.

Проверяются наличие занятия, отмена, начало, срок абонемента на текущую дату UTC включительно, остаток посещений и сумма мест активных броней всех пользователей. У пользователя может быть несколько броней одного занятия. Числовой несуществующий идентификатор возвращает `404`; неверные входные данные — `400`; бизнес-отказы — `409` с `reason` в ProblemDetails.

`GET /enrollments/{id}` возвращает свою бронь с занятием, залом и текущим абонементом. Запрос выполняется одним SQL без кэша, с обходом фильтра отменённых занятий. Отменённая бронь тоже доступна. Для отсутствующей или чужой брони все три новых маршрута возвращают `404`; нечисловой идентификатор — `400`, поэтому в маршрутах намеренно нет ограничения `{id:long}`, превращающего ошибку разбора в отсутствие маршрута.

`POST /enrollments/{id}/seats` принимает новое итоговое число мест. Увеличение проверяет срок, баланс и вместимость и списывает только разницу. Уменьшение возвращает разницу и доступно при истёкшем или исчерпанном абонементе. Равное число мест проверяет состояние брони и занятия, но не требует действующего абонемента. Ответ — полная карточка, прочитанная в той же транзакции после сохранения.

`POST /enrollments/{id}/cancel` освобождает активные места, сохраняя исходное `seats`. За два часа до старта включительно возвращает посещения, позже — нет. Для отменённого клубом занятия возвращает всё, в том числе после времени начала. Иначе после начала активную бронь отменить нельзя. Сумма возврата сохраняется в `RefundedVisits`; повтор возвращает её без повторного начисления, независимо от новых изменений состояния занятия.

## Транзакция и конкуренция

Операция выполняется в PostgreSQL в одной транзакции `Read Committed`. Порядок: запись идемпотентности → строка занятия → строка абонемента. Строки захватываются через `FOR UPDATE`; отменённое занятие читается с обходом существующего query filter. Активные места считаются отдельным запросом после захвата блокировок, с суммой типа bigint для защиты от переполнения.

Списание посещений, бронь и сохранённый ответ фиксируются вместе. Исключение до commit откатывает все изменения, включая вставленную запись ключа. Внутри транзакции нет обращений к Redis или внешним сервисам. Последующие операции записи должны соблюдать тот же порядок блокировок; при нескольких абонементах нужен стабильный порядок их захвата.

Уникальность абонемента пользователя и неотрицательный остаток дополнительно защищены ограничениями БД. Индекс `(class_id, status)` помогает считать активные места. Миграция создания брони добавляет отдельную таблицу идемпотентности и индексы, сохраняя исходные записи и балансы.

Изменение и отмена сначала определяют занятие по идентификатору своей брони, затем блокируют занятие → абонемент → бронь. После блокировок состояние перечитывается. Проверка владельца присутствует и при первоначальном поиске, и при захвате брони. Конкурентная отмена начисляет возврат один раз; совместные изменение и отмена используют то же согласование.

Миграция `EnrollmentRefunds` добавляет `refunded_visits`. Исходные отмены получают расчётный возврат: полное число мест, если занятие сейчас отменено клубом либо время отмены не позже двух часов до старта; иначе ноль. Seeder использует ту же формулу без изменения числа записей, исходных времён или балансов. Исторические журналы возвратов и время отмены занятия клубом отсутствуют, поэтому это реконструкция по сохранённому снимку, а не доказательство фактического старого начисления. Если время отмены отсутствует и занятие не помечено отменённым, принимается нулевой возврат. Повтор отмены старой брони не меняет текущий абонемент.

## Решения по свободным местам контракта

- Ключ идемпотентности независим для каждого пользователя и вида операции. Сейчас вид операции — `create-enrollment`.
- Тот же ключ с другими `classId` или `seats` возвращает `409 idempotency-key-reused`. Первоначальный результат сохраняется.
- Сравниваются разобранные значимые поля, а не исходный JSON. Порядок полей и неизвестные поля не влияют на повтор.
- На длину ключа прикладного ограничения нет. Хранится исходная строка; уникальный индекс использует SHA-256. Исходный ключ дополнительно сравнивается, поэтому коллизия не воспроизводит чужой ответ. Непустой ключ не нормализуется приложением.
- Конкурентная вставка одного ключа согласуется через `INSERT ... ON CONFLICT DO NOTHING`, затем отдельное чтение строки под блокировкой. Неуспешная операция откатывает ключ, и повтор может выполнить проверки заново.
- Повтор успешной операции возвращает первоначальный `201` и сохранённое тело, даже если бронь или абонемент впоследствии изменились. Результат сохраняется в той же транзакции, что и списание.
- При нескольких бизнес-нарушениях приоритет: отмена занятия, начало, срок абонемента, остаток посещений, вместимость. Успешный повтор проверяется раньше текущего состояния занятия и абонемента.
- Момент бизнес-проверок берётся через `TimeProvider` после ожидания блокировок. `createdAt` усекается до микросекунд для одинакового ответа из памяти и PostgreSQL.
- При изменении мест состояние отменённой брони проверяется раньше состояния занятия; затем отмена занятия, начало, а при увеличении — срок, баланс и вместимость. Повтор отмены проверяется раньше изменившихся бизнес-условий. Для исторических отмен применяется описанная выше реконструкция без нового начисления.
- Лимит запросов — скользящее окно 60 секунд. Атомарный Lua-скрипт Redis использует время сервера и допускает 60 запросов пользователя. После аутентификации запросы к отмеченным маршрутам учитываются до проверки роли и привязки модели, включая ответы `400`, `403` и `409`; отклонённые `429` не продлевают окно. Успешные повторы тоже учитываются. Запросы без действующей аутентификации, login и health не учитываются. Все восемь маршрутов используют ту же метку `EnrollmentRateLimit` и тот же счётчик пользователя.

## Запуск и проверки

Команды README и существующая конфигурация подключения сохранены. Для локального Podman зависимости запускаются из папки проекта:

```powershell
podman machine start
podman compose -p fitnessclub up -d
dotnet run --project WebApi
```

Если машина Podman уже работает, повторный `machine start` не нужен. В окружении с Docker используется штатный `docker compose up -d`.

```powershell
dotnet test
```

Тесты используют исходную фикстуру с отдельной PostgreSQL-базой и Redis database 1. Перед тестами этот Redis database очищается, как предусмотрено исходным проектом. Для проверки HTTP используется WebApplicationFactory; тест отдельно подтверждает подключение именно к тестовой БД.

В Swagger объявлены обязательный заголовок `Idempotency-Key` и Bearer JWT для защищённых операций. Для ручной проверки: войти через `/auth/login`, скопировать `accessToken`, нажать Authorize и вставить токен, затем выполнить `/schedule` с `from` и `to` либо `/enrollments` с новым ключом. Сам login остаётся публичным.

Ключ подписи JWT не хранится в проекте: для локального запуска он может задаваться через .NET User Secrets, для рабочего окружения — через `Jwt__Key`. Если ключ не задан в Development или Testing, создаётся случайный временный ключ в памяти, чтобы сохранить исходную команду запуска; выданные им токены не переживают перезапуск. В остальных окружениях отсутствие ключа вызывает ошибку. Во всех случаях требуется ключ длиной не менее 32 байт UTF-8; тестовая фабрика создаёт отдельный случайный ключ. Подготовка постоянного локального ключа описана в `README.md`.

Если локальный корпоративный NuGet-источник отвечает `401`, разово восстановить публичные пакеты можно командой:

```powershell
dotnet restore --source https://api.nuget.org/v3/index.json
dotnet test --no-restore
```

## Решения для очереди

Таблица `waitlist_entries` хранит ожидания постоянно; состояние в памяти API не является источником истины. У пользователя допускается максимум одна запись `waiting` на занятие (частичный уникальный индекс). Позиция считается среди ожидающих по `(created_at, id)` и не хранится отдельным счётчиком.

`POST /enrollments/waitlist` требует ключ идемпотентности. Ключ имеет тот же scope «пользователь + операция», что и создание брони. Тот же запрос возвращает первоначальный `201` и позицию на тот момент. Повтор ключа с другим классом или количеством мест даёт `idempotency-key-reused`. Бизнес-отказы не закрепляют ключ.

Продвижение выполняется синхронно в той же транзакции, что отмена брони или уменьшение числа мест. Абонементы текущего пользователя и ожидающих блокируются в одном порядке по `user_id`, затем блокируется изменяемая бронь. FIFO сортируется независимо по `created_at, id`. Ожидающий с недействующим/недостаточным абонементом снимается без списания, после чего проверяется следующий. Первый подходящий ожидающий, которому не хватает освободившихся мест, остаётся ждать, а следующих не обходим. Запрос, превышающий полную вместимость класса, снимается как невозможный и не блокирует очередь.

После исполнения ожидание получает статус `fulfilled` и идентификатор созданной брони. Попытка отменить исполненное ожидание возвращает `409 waitlist-fulfilled`; отменять нужно соответствующую бронь. Отмена ожидания в состоянии `waiting` идемпотентна и возвращает `200 cancelled` при повторах. При отмене клубом/старте новые брони очереди не создаются.

## Решения для расписания

`GET /schedule` доступен любому пользователю с JWT. `from` и `to` обязательны и принимаются только как ISO 8601 date-time. Время без смещения считается UTC; время со смещением переводится в UTC. Выборка использует интервал `[from, to)`, отменённые занятия скрываются глобальным фильтром EF. Необязательный `roomId` при отсутствии совпадений возвращает пустую страницу. Размер по умолчанию — 20, разрешён диапазон 1–100.

Сортировка выполняется по `(starts_at, id)`: id задаёт стабильный порядок занятий с одинаковым временем. Курсор в Base64URL содержит последнюю пару сортировки и фильтры `from`, `to`, `roomId`; несовпадение фильтров или повреждённый токен даёт `400`. `limit` в курсоре не фиксируется и может меняться между страницами.

Страница и оба агрегата возвращаются одним SQL-запросом: `freeSeats = max(0, capacity - активные места всех пользователей)`, `mySeats = активные места текущего пользователя`. Так значения соответствуют одному снимку PostgreSQL. Новые составные индексы `(starts_at, id)` и `(room_id, starts_at, id)` поддерживают листание без `OFFSET` как с фильтром зала, так и без него. Маршрут использует тот же Redis-лимит 60 запросов в минуту на пользователя.

## Решения для аналитики

`GET /analytics/load` доступен только роли `admin`; авторизованный пользователь без этой роли получает `403`. Даты принимаются только в формате `yyyy-MM-dd`; диапазон включительный с обеих сторон, одинаковые даты разрешены. Период преобразуется в UTC-интервал от начала `from` до начала дня после `to`, чтобы использовать индекс по времени занятия; для максимальной даты верхняя граница не задаётся.

PostgreSQL одной командой отбирает занятия диапазона и считает строки по `(UTC-дата начала, зал)`. `LEFT JOIN LATERAL` суммирует активные брони для каждого выбранного занятия. Отменённые клубом занятия исключаются до группировки; отменённые брони не учитываются. Результат отсортирован по дате и ID зала; фильтр по несуществующему залу возвращает пустой `items`. На маршруте действует общий Redis-лимит 60 запросов в минуту.

## Оставшаяся работа и ограничения

Все функциональные маршруты ТЗ реализованы. Кэш карточки не добавлялся. Внешние изменения таблиц в обход принятого порядка блокировок не защищаются блокировкой строки занятия сами по себе; нагрузочная проверка на сотнях тысяч записей ещё не выполнялась.

Автоматические повторы транзакций при deadlock или потере соединения не добавлены; безопасный повтор успешного запроса обеспечивается ключом идемпотентности. HTTP-сервер сохраняет стандартные инфраструктурные ограничения на общий размер заголовков. Состояние лимитера при недоступности Redis не подменяется локальным счётчиком.

Проверены: точный ответ и списание; валидация тела и заголовка; все причины отказа; безопасный повтор и конфликт payload; независимость пользователей; несколько броней; актуальный подсчёт активных мест; длинный ключ; конкурентная запись на последнее место; общий абонемент на разные занятия; параллельные повторы ключа; ожидание реальной PostgreSQL-блокировки с чтением нового баланса; откат при ошибке сохранения ответа; лимит 60 запросов и его атомарность.

Для карточки, изменения и отмены добавлены проверки закрытых вложенных моделей, актуального баланса, отменённых занятий и броней, чужих идентификаторов, аутентификации, неверных path/body, увеличения/уменьшения/равного числа мест, двухчасовой границы, старта занятия и повторов отмены. Проверены совместный лимит маршрутов, конкурентные отмены, совместные изменение/отмена, общий абонемент при увеличениях разных занятий и откат при исключении после исполнения SQL. Историческая отмена возвращает сохранённый расчётный результат без начисления.

Для расписания проверены обязательность и формат дат, UTC для времени без смещения, границы `[from, to)`, сортировка/пагинация при одинаковом времени начала, изменение размера страницы между запросами, привязка токена к фильтрам, фильтр по залу, скрытие отменённых занятий, свободные и собственные места, отсутствие аутентификации и общий лимит запросов.

Для аналитики проверены корректность группировки по UTC-дате и залу, обе включительные границы дат, фильтр зала, суммы вместимости и только активных мест, исключение отменённых занятий и броней, пустой результат для неизвестного зала, ошибки параметров, `401`/`403`, общий лимит и учёт `403`-запросов в общей квоте всех маршрутов.

Миграции проверены на новой тестовой БД и на отдельной заполненной БД, приведённой к исходной схеме. Значения исходных полей всех пяти таблиц до и после обновления совпали; новое поле возврата проверено по формуле для каждой записи; расхождений модели и migration snapshot нет. Штатный запуск применил пятую миграцию к локальной базе: сохранены 205 пользователей, 305 броней и общий остаток 4126 посещений; таблица очереди пуста. `/health` и Swagger вернули `200`; расписание, аналитика и оба маршрута очереди опубликованы в OpenAPI. Проверка аналитики на локальных данных вернула `200` администратору и `403` обычному пользователю. После проверки API остановлен, зависимости оставлены работающими.
